# Лучшие практики создания скилов для агентов (Hermes & Antigravity)

Данный документ обобщает стандарты и архитектурные рекомендации по проектированию автономных навыков (skills), обеспечивающие высокую надёжность, экономию контекстного окна и замкнутый цикл верификации.

---

## 1. Анатомия структуры скила

Каждый навык размещается в отдельной директории внутри каталога `skills/` (в проекте или в `~/.hermes/skills/`) со следующей организацией:

```text
skills/<skill_name>/
├── SKILL.md            # [Обязательно] Главный файл инструкций с YAML frontmatter
├── scripts/            # [Опционально] Исполняемые скрипты автоматизации и CLI
├── references/         # [Опционально] Детальная документация, схемы API, мануалы
├── examples/           # [Опционально] Образцы входных/выходных данных, тест-кейсы
└── resources/          # [Опционально] Шаблоны, промпты, конфигурации
```

---

## 2. Принцип прогрессивного раскрытия (Progressive Disclosure)

- **Краткий `SKILL.md`**: Модель читает `SKILL.md` только при активации скила. Основной файл не должен содержать гигантских дампов кода или длинных теоретических описаний.
- **Ссылки на `references/`**: Тяжёлые архитектурные описания и спецификации выносятся в `references/`. Агент переходит по ссылкам только при необходимости конкретизации деталей.
- **Инкапсуляция в `scripts/`**: Сложная логика (парсинг логов, вычисление статистических метрик, запросы к API) оформляется в виде готовых Python/Bash-скриптов с понятными CLI-аргументами. Агент запускает скрипт одной командой вместо генерации сотен строк временного кода.

---

## 3. Спецификация YAML Frontmatter

Каждый `SKILL.md` обязан начинаться с блока метаданных:

```yaml
---
name: laya-train
description: >-
  Используется для сбора обучающих выборок из сессий Hermes и логов плагина,
  разметки данных с помощью основной модели (Teacher LLM), тестирования точности Laya
  до и после обучения, запуска fine-tuning и формирования отчетов.
version: 1.0.0
license: MIT
metadata:
  hermes:
    tags: [laya, system1, training, fine-tuning, eval, distillation]
---
```

### Ключевые требования к описанию (`description`):
1. **Формулировка от 3-го лица**: Описание предназначено для мета-планировщика, выбирающего подходящий инструмент или скилл.
2. **Чёткие условия активации**: Должно быть однозначно понятно, **что** скилл делает и **при каких запросах** пользователя его следует запустить.

---

## 4. Разметка данных и привлечение основной модели (Teacher Model)

В реальных агентных системах логи содержат:
1. **Явные действия**: Запросы, где агент вызвал конкретный инструмент (`read_file`, `terminal`, `mcp__marketplace__ozon_search`). Здесь действие служит готовым эталоном (Ground Truth).
2. **Диалоговые ответы**: Реплики без вызова инструментов.
3. **Неоднозначные или неполные ходы**: Запросы, где инструмент не вызывался, но теоретически мог требоваться, либо где агент ошибся.

### Лучшая практика (LLM-as-a-Teacher / Distillation):
Когда в сессии отсутствует явный вызов инструмента или нужно подтвердить правильность выбора, формируется запрос к **основной модели Hermes** (Primary LLM) с экспертным промптом. Основная модель выступает в роли «Учителя» (Teacher Judge), определяя категорию, решение и список инструментов.

---

## 5. Замкнутый цикл верификации (Evaluation Closed Loop)

Навык обучения не должен завершаться «вслепую». Он обязан включать три обязательные фазы:

1. **Pre-Training Evaluation**:
   - Замер точности (Accuracy), Brier score, Mean Confidence на зафиксированной валидационной выборке (`eval.jsonl`) на текущей версии модели.
2. **Обучение и перезагрузка**:
   - Обучение весов (`laya-train`).
   - Компиляция GGUF для инференса (`ggmlc`).
   - Горячая перезагрузка сервера (`POST /reload`).
3. **Post-Training Evaluation & Report**:
   - Повторный замер метрик на той же выборке `eval.jsonl`.
   - Расчёт изменений ($\Delta \text{Accuracy}$, $\Delta \text{Brier Score}$, $\Delta \text{Confidence}$).
   - Сводный отчёт в Markdown с детализацией по категориям инструментов.
